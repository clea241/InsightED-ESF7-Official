## Finding details

### 1. missing-limit - `server/controllers/workload_rows/index.js:145` (High, Verified, access layer: raw-pg)

- **What the code does:** `GET /` runs `SELECT * FROM esf7_workload_rows ORDER BY created_at ASC` with no `WHERE` and no `LIMIT`, then maps every row through `formatWorkloadRecord`.
- **Plan evidence:** top node `Gather Merge`, estimated 652,690 rows vs actual 651,940 (loops 1), 1,368 ms at that node; child `Sort` is `external merge` on `Disk` (estimated 271,954 vs actual 217,313 per worker, 3 loops, 828 ms per loop); leaf `Seq Scan` on `esf7_workload_rows`. Actual execution time 1,443 ms recorded (1,655 ms warm). Temp blocks written 97,754; shared read 51,484. Plan width 736 bytes, so about 480 MB of rows would be sorted and sent. Table has 652,689 rows. Plan file `docs/orm-optimizer/plans/workload-rows-list-all.json`.
- **Why it matters:** a single request touches the whole table and builds a response of every teacher's workload from every school. The cost grows with the table. The Seq Scan itself is expected here; the issues are the unbounded result (reading-explain threshold 4) and the disk spill (threshold 2). No index change helps.
- **Suggested fix (not applied):** require a school (or personnel) scope in the `WHERE`, return a page (`LIMIT`/keyset on `(created_at, id)`), and select only the columns the client uses (not `raw_payload`). If the route is unused, remove it.
- **Follow-up (2026-10-10):** fixed on `esf7_local` only. Route now pages by keyset on `(created_at, id)` with a new index; same query shape with `LIMIT 101` went from 1,443 ms (full list) / 324 ms (page, no index) to 0.126 ms, Index Scan, no sort, no spill. Plans: `workload-rows-page1-before.json`, `workload-rows-page1-after.json`, `workload-rows-page-deep-before.json`, `workload-rows-page-deep-after.json`. Not applied to production.
- **Other sites in this group:** `select-all` at `workload_rows/index.js:995` (filtered by personnel, same shape as the Rejected plan below) and `shs_workload_rows/index.js:72` (missing-limit on `esf7_shs_workload_rows`, 0 rows locally, Static only).

### 2-7 and 9. duplicated-json-payload (access layer: raw-pg; schema columns are declared in Drizzle `schema.ts`)

What the code does: each write below runs `INSERT ... (typed columns..., raw_payload)` or `UPDATE ... SET raw_payload = $n` and passes `JSON.stringify(req.body)`, `JSON.stringify({ ...row, ... })` or the whole row object as the payload, in the same statement that writes the typed columns. The read side then merges `row.raw_payload` back into the response (`const raw = row.raw_payload || {}` in each controller's formatter). Row contents were not read or saved; sizes and key names only. ### 8. write-in-loop - `server/controllers/workload_rows/index.js:689` (Medium, Static only, access layer: raw-pg)

- **What the code does:** the bulk save deletes a teacher's workload rows, then loops `rowsToSave` (line 622) and runs one `INSERT` per row via `client.query` (line 689); the SHS (loop at line 720, insert at `:728` into `esf7_shs_workload_rows`), teaching-related (loop 773, insert `:814` into `esf7_related_task`) and administrative (loop 849, insert `:910` into `esf7_admin_task`) loops do the same.
- **Plan evidence:** none. Inserts cannot be explained by this skill. Sizing from the local data: average 6 and maximum 200 rows per teacher, so a save costs 6 to 200 round trips per table.
- **Why it matters:** each insert is a separate round trip inside one transaction; at the 200-row maximum that is hundreds of calls for one teacher, and a school save multiplies it by the number of teachers if the client sends them one by one. Not shown to be slow at the typical size of 6.
- **Suggested fix (not applied):** build one multi-row statement per table (`INSERT ... VALUES ($1..), ($n..)` or `unnest` arrays), chunked to stay under 65,535 parameters, inside the same transaction.
- **Other sites in this group:** `workload_rows/index.js:728, 814, 910`.
